# Интеллектуальная маршрутизация обращений студентов — дизайн

Дата: 2026-09-25
Контекст: кейс-задача №3 индивидуального задания на производственную практику
(Университет «Синергия», направление 09.03.03, профиль «ИИ и большие данные»).

## 1. Цель

Показать интеграцию ИИ в бизнес-процесс университета: обработку входящих
обращений студентов. Программа должна наглядно покрывать все 5 этапов задания:

| Этап задания | Чем закрывается в программе |
|---|---|
| Анализ бизнес-процессов | `docs/business_process.md`: процесс «как было / как стало», узкие места |
| Выбор технологий ИИ | `docs/technology_choice.md`: сравнение подходов, обоснование выбора |
| Разработка и внедрение | Модель классификации + веб-приложение оператора |
| Обучение сотрудников | Страница «Обучение» в приложении + `docs/user_guide.md` |
| Мониторинг и анализ | Страница «Мониторинг»: метрики, журнал, динамика; отчёт оценки модели |

Критерии успеха:
- `pip install -r requirements.txt` → `python -m router.train` → `streamlit run app/main.py`
  работает на чистой машине без GPU и без внешних API.
- Точность классификации по отделам на тестовой выборке ≥ 85 % (macro-F1 ≥ 0.85).
- Все тесты (`pytest`) проходят.
- README достаточно, чтобы преподаватель понял задачу, запустил и увидел результат.

Допущения: реальных данных университета нет — используется синтетический
датасет, сгенерированный по шаблонам. Это явно указывается в документации.

## 2. Предметная область

Отделы (классы маршрутизации):
1. Деканат (академические вопросы: пересдачи, академический отпуск, перевод)
2. Учебный отдел (расписание, сессия, зачётная книжка, учебный план)
3. Бухгалтерия (оплата обучения, договоры, налоговый вычет, рассрочка)
4. Приёмная комиссия (поступление, документы абитуриента, вступительные)
5. IT-поддержка (личный кабинет, LMS, пароль, доступ к вебинарам)
6. Справочный центр / документы (справки об обучении, копии, архив)
7. Практика и трудоустройство (места практики, договоры с организациями, вакансии)
8. Студенческий офис / общежитие и внеучебная деятельность

Срочность: `высокая` / `обычная` — определяется правилами по ключевым словам
(«срочно», «завтра экзамен», «не могу сдать», «сегодня дедлайн» и т. п.).
Это осознанно простое решение; ML используется для отдела.

## 3. Архитектура

```
final_practice/
├── router/                  # ядро (без зависимостей от UI)
│   ├── config.py            # пути, порог уверенности, список отделов
│   ├── data_generator.py    # синтетический датасет обращений
│   ├── preprocessing.py     # нормализация текста
│   ├── model.py             # обучение, сохранение/загрузка, predict
│   ├── urgency.py           # правила срочности
│   ├── service.py           # RequestRouter: классификация + решение авто/ручной
│   ├── storage.py           # SQLite-журнал обращений и исправлений
│   ├── metrics.py           # расчёт метрик мониторинга по журналу
│   ├── train.py             # CLI: генерация данных → обучение → отчёт
│   └── simulate.py          # CLI: имитация потока обращений для мониторинга
├── app/
│   ├── main.py              # Streamlit, навигация
│   └── pages/ (operator, monitoring, training)
├── data/                    # dataset.csv, router.db (генерируются)
├── models/                  # model.joblib, report.json (генерируются)
├── docs/                    # документация по этапам
├── tests/
├── requirements.txt
└── README.md
```

### Компоненты

- **data_generator** — шаблоны фраз на отдел × подстановки (дисциплины, даты,
  формулировки, вежливые обороты, опечатки/шум). `generate(n, seed) -> DataFrame[text, department]`.
  Детерминирован при фиксированном seed. ~2400 записей (300 на отдел).
- **preprocessing** — нижний регистр, `ё→е`, удаление пунктуации/лишних пробелов.
- **model** — `Pipeline(TfidfVectorizer(word 1–2-грамм) + TfidfVectorizer(char 3–5-грамм), LogisticRegression)`.
  Char-n-граммы дают устойчивость к опечаткам и словоформам без морфологического
  анализатора. `train(df) -> (pipeline, report)`, `save/load` через joblib,
  `predict_proba(texts)`.
- **service.RequestRouter** — `route(text) -> RoutingResult(department, confidence,
  urgency, auto_routed, top3)`. Если `confidence < threshold` (по умолчанию 0.6) —
  `auto_routed=False`, обращение попадает в очередь ручного разбора.
- **storage** — SQLite, таблица `requests(id, created_at, text, predicted, confidence,
  urgency, auto_routed, final_department, corrected, processed_at)`.
  Функции: `log_request`, `confirm`, `correct`, `pending`, `all_requests`, `corrections`.
- **metrics** — по журналу: доля автомаршрутизации, точность модели по
  подтверждённым/исправленным (accuracy = 1 − доля исправлений), распределение
  по отделам, средняя уверенность, динамика по дням, оценка сэкономленного
  времени (ручная маршрутизация ≈ N мин/обращение — параметр в config).
- **train (CLI)** — генерирует датасет (если нет), делит 80/20 stratified,
  обучает, печатает classification report, сохраняет `models/report.json`
  (accuracy, macro-F1, per-class, confusion matrix). Флаг `--with-corrections`
  добавляет исправления операторов из БД в обучающую выборку (цикл дообучения).
- **simulate (CLI)** — прогоняет N новых обращений (отдельный seed) через роутер,
  с заданной вероятностью имитирует исправление оператором, раскидывает даты по
  последним 30 дням — чтобы дашборд мониторинга был наполнен.

### Веб-приложение (Streamlit)

1. **Оператор** — поле ввода обращения (или «взять пример»), результат:
   отдел, уверенность, топ-3, срочность, пометка «авто/ручной разбор».
   Кнопки «Подтвердить» / выбор другого отдела + «Исправить». Ниже — очередь
   ручного разбора.
2. **Мониторинг** — KPI-плитки (всего обращений, доля авто, точность, сэкономлено
   часов), график по дням, распределение по отделам, качество модели из
   `report.json` (метрики по классам, матрица ошибок), последние исправления.
3. **Обучение** — краткая инструкция для сотрудника (как работать, что значит
   уверенность, когда исправлять), FAQ, кнопка «Переобучить модель с учётом
   исправлений» с показом метрик до/после.

## 4. Обработка ошибок

- Нет обученной модели → приложение показывает сообщение с командой обучения,
  не падает.
- Пустой/слишком короткий текст (< 3 символов после нормализации) → ошибка
  валидации в `route()` (`ValueError`), UI показывает предупреждение.
- БД создаётся автоматически при первом обращении.

## 5. Тестирование (pytest)

- generator: детерминизм, баланс классов, непустые тексты.
- preprocessing: регистр, ё, пунктуация.
- model: обучение на сгенерированных данных даёт macro-F1 ≥ 0.85 на отложенной выборке;
  save/load сохраняет предсказания.
- urgency: срабатывание на ключевых словах и отсутствие ложных на нейтральных.
- service: низкая уверенность → `auto_routed=False`; пустой текст → `ValueError`.
- storage + metrics: на временной БД — лог, подтверждение, исправление, корректные метрики.

## 6. Вне рамок (YAGNI)

Авторизация, интеграция с реальной CRM/почтой, нейросетевые модели/LLM,
Docker, деплой. Упоминаются в документации как направления развития (пригодится
для кейсов 4–5).
